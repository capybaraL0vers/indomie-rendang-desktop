Cara menemukan dan memahami 7 bug, dari nol

Ditulis untuk kamu yang belum pernah menyentuh Rust. Mulai dari teori, lalu project, lalu tiap bug dengan kode aslinya.

Bagian 0

Mulai dari sini

Panduan ini ditulis seolah kamu belum pernah melihat Rust sama sekali. Urutannya sengaja begini: (1) kenal dulu project-nya, (2) belajar cara mencari bug, (3) belajar teori dasar Rust, (4) baru lihat ketujuh bug satu per satu dengan kode aslinya, (5) fitur tambahan, (6) bahan presentasi.

🔑Tiga aturan emas untuk pemula

1. Error itu bukan musuh, error itu petunjuk. Compiler Rust terkenal cerewet, tapi pesannya hampir selalu menunjuk baris yang salah dan sering menulis cara memperbaikinya.

2. Ubah satu hal, lalu cek lagi. Jangan memperbaiki sepuluh hal sekaligus. Kalau error bertambah, kamu langsung tahu penyebabnya.

3. Pahami sebelum menyalin. Soal TPA bilang: komponen yang tidak bisa dijelaskan atau didemokan bisa dinilai 0. Jadi tujuan utamamu bukan sekadar "bug hilang", tapi bisa menjawab "kenapa ini bug, dan kenapa perbaikanmu benar?"

Cara membaca panduan ini

  • KODE Blok gelap berisi kode asli dari project. Baris merah (−) = kode lama yang bermasalah, baris hijau (+) = kode setelah diperbaiki, baris kuning (▶) = baris yang perlu kamu perhatikan.
  • TERMINAL Blok hitam berisi output terminal asli yang muncul saat project ini dikompilasi (ini pengganti screenshot, bedanya bisa kamu salin dan cari di Google).
  • UJI DIRIMU Kotak "❓" bisa diklik untuk melihat jawaban. Coba jawab dulu dalam hati sebelum membuka.
  • Kotak 🎤 Kalimat untuk penguji adalah contoh penjelasan singkat yang bisa kamu ucapkan saat presentasi, ubah dengan kata-katamu sendiri.
ℹ️Kejujuran soal bug ke-7 (Rust Tauri)

Enam bug sudah terbukti (error compiler atau perilaku aplikasi yang bisa didemokan). Bug Rust Tauri punya bukti kuat tapi tidak sepasti yang lain, dan di bagian 4 saya tulis apa adanya, termasuk apa yang masih mungkin meleset.

Bagian 2

Cara menemukan bug, langkah demi langkah

Ini bagian yang kamu tanyakan: apa yang harus dilakukan pertama kali. Tidak ada sihir, hanya urutan yang konsisten.

  1. Baca soalnya dengan teliti

    Soal berkata: 7 bug, 5 di server dan 2 di aplikasi Tauri. Di rubrik penilaian, bobotnya: Import 3, Trait 2, Async/Await 2, Ownership 2, ActiveModel 4, React 2, Rust Tauri 2. Nama kategori di rubrik adalah petunjuk jenis bug. Kamu tahu jenis dan tempatnya sebelum membuka satu berkas pun.

  2. Cari tulisan petunjuk di dalam kode

    Pembuat soal meninggalkan komentar yang menunjukkan area aman. Contoh aslinya ada tepat di bawah daftar langkah ini.

  3. Siapkan alat

    Kamu butuh: Rust (cargo), Node.js (npm), dan MariaDB dari XAMPP (database rhodev_island_logistic, file SQL ada di server/src/database/create+insert.sql, impor lewat phpMyAdmin).

  4. Jalankan cargo check dan baca error dari ATAS

    Ini langkah paling ampuh untuk bug jenis compile (Import, Trait, Async, Ownership). Penjelasan lengkap di bagian 2.2.

  5. Untuk bug yang TIDAK error: bandingkan, ikuti jalur, lalu uji

    ActiveModel, React, dan Rust Tauri tidak membuat compiler berteriak, aplikasinya jalan tapi salah. Caranya ada di bagian 2.3.

  6. Perbaiki satu, kompilasi ulang, catat

    Tulis di catatan: bug apa, di berkas mana, penyebab, perbaikan. Catatan ini nanti jadi bahan presentasimu.

✅Cara memakai petunjuk itu

Anggap semua tempat yang berkomentar "ga ada bug di sini" sebagai area aman, jangan buang waktu di sana. Maka bug Tauri hanya mungkin ada di controller/courier_controller.rs, controller/dispatcher_controller.rs, lib.rs, atau berkas model/ dan tampilan React. Ruang pencarian langsung mengecil.

Bagian 3

Teori dasar Rust dari nol

Bagian ini lengkap tapi pendek. Setiap konsep punya tiga hal: idenya (dengan analogi), contoh kecil, dan kaitannya dengan bug di project ini. Kamu tidak perlu hafal, cukup paham idenya sampai bisa menjelaskan dengan kata sendiri.

3.1 Program pertama dan cara "print" di Rust

  • fn main(): pintu masuk program. Program mulai berjalan dari sini.
  • println!(...): mencetak satu baris ke layar. Tanda ! berarti ini macro (semacam fungsi spesial); cukup ingat bahwa print selalu ditulis println!, bukan println.
  • {} adalah lubang yang diisi nilai di belakangnya. println!("{} + {} = {}", 1, 2, 3) mencetak 1 + 2 = 3.
  • Setiap perintah diakhiri ; (titik koma).
✅Kegunaan di project ini

Di project ini print dipakai untuk memberi tahu kita sesuatu. Contohnya di log_activity: eprintln!("Failed to record activity log: {error}"). Huruf e di depan berarti mencetak ke jalur error (stderr), dan {error} langsung memasukkan variabel bernama error.

3.2 Variabel: let dan mut

Di banyak bahasa variabel boleh diubah kapan saja. Di Rust, secara default variabel dikunci (immutable). Kalau mau bisa diubah, harus ditulis mut (singkatan mutable = dapat diubah).

💡Analogi: kotak dengan gembok

let x = 5 seperti menaruh barang di kotak bergembok: kamu boleh melihat isinya, tapi tidak boleh mengganti. let mut x = 5 adalah kotak tanpa gembok. Alasannya keamanan: kalau banyak bagian program memegang variabel yang sama, Rust ingin kamu yang menyatakan dengan sadar bahwa isinya akan berubah.

3.3 Fungsi dan nilai kembalian

  • Parameter wajib ditulis tipenya: a: i32.
  • -> i32 menyatakan tipe nilai yang dikembalikan.
  • Baris terakhir tanpa titik koma otomatis menjadi nilai kembalian. Kalau ingin keluar lebih awal, pakai return, seperti di kode project: return Err(StatusCode::BAD_REQUEST);.

struct adalah cetakan data (mirip class tanpa perilaku). impl menempelkan fungsi pada struct itu.

Di project ini struct dipakai untuk DTO (bentuk data HTTP) dan entity (bentuk tabel). Contoh: OrderItemResponse dan OperatorDetailsResponse.

3.5 Ownership (kepemilikan) dan Borrowing (peminjaman)

Ini konsep terpenting dan paling khas dari Rust. Rust tidak memakai garbage collector seperti Java, jadi ia butuh aturan tegas kapan sebuah data boleh dihapus. Aturannya hanya tiga:

🔑Tiga aturan ownership

1. Setiap nilai punya satu pemilik.

2. Hanya boleh ada satu pemilik pada satu waktu. Kalau dipindah, pemilik lama kehilangan akses (disebut move).

3. Kalau pemiliknya selesai (keluar dari { }), nilainya otomatis dibuang.

💡Analogi: buku perpustakaan

Bayangkan satu buku yang punya tepat satu pemilik. Kalau kamu memberikan bukunya ke temanmu (move), kamu tidak punya buku itu lagi. Kalau kamu cuma meminjamkan (borrow, ditulis &), bukunya tetap milikmu. Temanmu boleh membaca. Untuk mencoret-coret bukunya (&mut), hanya satu peminjam boleh pada satu waktu, supaya tidak ada dua orang menulis di halaman yang sama.

DitulisArtinyaBoleh dibaca?Boleh diubah?Berapa peminjam?
xmemilikiyahanya jika let mut1 pemilik
&xpinjam bacayatidakboleh banyak sekaligus
&mut xpinjam ubahyayahanya 1 pada satu waktu

Hubungan dengan bug "Ownership" di project ini

Di project ini bug kategori Ownership berwujud error E0596: cannot borrow ... as mutable, as it is not declared as mutable. Artinya: kode meminjam variabel untuk diubah (&mut), tapi variabelnya tidak dideklarasikan mut.

Kenapa .push() butuh &mut? Karena push menambah isi vector, jadi ia harus meminjam vector itu untuk diubah. Bukunya harus boleh dicoret.

ℹ️Catatan kejujuran

Secara istilah, kategori Ownership di soal luas (move, borrow, mut). Yang ditanam di project ini adalah varian paling sederhana: lupa mut. Kalau penguji bertanya, jelaskan juga move dan borrow dengan buku perpustakaan di atas untuk menunjukkan kamu paham konsep besarnya.

Kenapa Rust mengunci variabel secara default? Bukankah merepotkan?

Supaya program lebih aman. Kalau sebuah variabel tidak pernah berubah, kita tidak perlu khawatir bagian lain mengubahnya diam-diam. Saat memang perlu berubah, mut adalah tanda yang jelas bagi pembaca kode.

3.6 Option, Result, dan match

Rust tidak punya null. Sebagai gantinya ada dua "kotak" yang memaksa kamu menangani kemungkinan gagal:

KotakIsi yang mungkinDipakai kalau
Option<T>Some(nilai) atau Nonenilainya mungkin tidak ada (misal kurir belum ditunjuk)
Result<T, E>Ok(nilai) atau Err(galat)operasinya mungkin gagal (misal query database)

Contoh nyata dari project (service.rs):

  • .is_err() bertanya "apakah ini Err?". .unwrap() mengambil isi Ok, tapi program crash (panic) kalau ternyata Err. Karena itu project ini selalu memeriksa is_err() dulu sebelum unwrap().
  • StatusCode::NOT_FOUND, BAD_REQUEST, INTERNAL_SERVER_ERROR adalah kode HTTP (404, 400, 500) yang dikirim balik ke pemanggil.
  • into_option() mengubah relasi SeaORM menjadi Option supaya bisa di-match.

3.7 Modul: mod, pub, dan use (inti bug Import)

Berbeda dengan Python atau JavaScript, Rust tidak otomatis melihat semua berkas di folder. Sebuah berkas baru dianggap "tidak ada" sampai ada yang mendaftarkannya. Dua perintah yang berbeda fungsi, dan sering tertukar:

💡Analogi: gedung apartemen

Folder entity/ adalah gedung. Setiap berkas (order.rs, operator.rs) adalah satu penghuni. Berkas mod.rs adalah buku daftar penghuni di lobi. Kalau penghuninya tidak tercatat di buku (pub mod order;), satpam (compiler) bilang "orang ini tidak ada di gedung ini", walaupun kamar fisiknya ada. Sedangkan use seperti menyimpan nomor kamar di HP supaya tidak perlu menyebut alamat lengkap tiap kali.

Apa bedanya error E0432 dengan E0425?

E0432 (unresolved import): kamu menulis use ke jalur yang tidak ada, biasanya karena modulnya belum didaftarkan dengan mod. E0425/E0422 (cannot find ...): kamu memakai sebuah nama yang belum diimpor sama sekali. Di project ini keduanya muncul, dan dua perbaikannya memang berbeda: tambah pub mod di mod.rs, dan tambah use di service.rs serta service_trait.rs.

3.8 Trait (kontrak) dan impl

Trait adalah daftar kemampuan yang wajib dimiliki sebuah tipe. Tipe yang mau "menandatangani" kontrak itu menulis impl NamaTrait for Tipe.

💡Analogi: SIM dan kemampuan menyetir

Trait seperti syarat resmi "pengemudi": bisa menyalakan mesin, menyetir, mengerem. Siapa pun yang mengaku pengemudi harus punya semua kemampuan itu. Tapi kalau kamu mengaku bisa "terbang" padahal tidak tertulis di syarat resmi, itu bukan bagian kontrak, jadi ditolak (E0407).

Di project ini kontraknya bernama ServiceTrait, dan pelaksananya adalah Service. Aturannya berlaku dua arah:

  1. Semua fungsi yang ditulis di impl ServiceTrait for Service harus ada di trait (kalau tidak → E0407).
  2. Kode yang memakai service lewat tipe generik (Arc<S> dengan S: ServiceTrait) hanya boleh memanggil fungsi yang tercantum di trait (kalau tidak → E0599: no method named ... found).

impl Future<Output = X> + Send terdengar menakutkan, tapi artinya sederhana: "fungsi ini async; hasil akhirnya bertipe X". Pada impl-nya cukup ditulis async fn ... -> X. Bagian + Send hanya menjamin hasilnya aman dipakai server yang menjalankan banyak tugas bersamaan.

3.9 async dan .await

Mengambil data dari database atau dari internet itu lambat. Kalau program berdiri menunggu, ia tidak bisa melayani orang lain. Async adalah cara agar program bilang: "selagi menunggu ini, kerjakan hal lain dulu."

💡Analogi: pesan makanan dengan nomor antrean

Kamu memesan di kasir dan menerima nomor antrean (itu Future). Nomor antrean itu bukan makanannya. Kamu baru punya makanan setelah menunggu dan menukarkan nomor itu (itu .await). Kalau kamu langsung bilang "ini makananku!" sambil memegang nomor antrean, kamu keliru. Itu persis bug Async/Await.

  • async fn tidak langsung berjalan. Ia mengembalikan Future (janji hasil).
  • .await berarti "tunggu sampai selesai, lalu beri aku hasilnya". Hanya boleh dipakai di dalam fungsi async.
  • Yang menjalankan semua ini adalah tokio (lihat #[tokio::main] di main.rs).
⚠️Kenapa error-nya aneh?

Kalau lupa .await lalu kamu coba match hasilnya dengan Ok(..)/Err(..), compiler protes: "expected associated type, found Result<_, _>". Terjemahannya: "aku mengharapkan sebuah Future (tipe asosiasi), tapi kamu memperlakukannya seperti Result".

🔑Inti yang harus diingat

SeaORM hanya menulis kolom yang kamu Set. Kalau kamu lupa Set sebuah kolom, tidak ada error, tidak ada peringatan. Kolom itu cuma tidak berubah. Karena itu bug ActiveModel sulit dilihat: kodenya valid dan programnya jalan, tapi sebuah perubahan penting tidak pernah tersimpan.

Apa bedanya Unchanged dan NotSet? Keduanya "tidak mengubah", kan?

Bedanya di informasi. Unchanged(2) tetap membawa nilai 2, sehingga SeaORM tahu ini baris dengan id = 2 dan bisa memakainya di WHERE. NotSet tidak membawa apa pun. Itu sebabnya primary key (id) ditulis Unchanged, sedangkan kolom lain yang tidak ingin disentuh dibiarkan NotSet lewat ..Default::default().

Bagian B — masalah N+1 pada daftar warehouse

💡Analogi: bertanya satu-satu

Kamu ingin tahu isi 20 kulkas. Cara N+1: tanya "ada daftar kulkas?" (1 pertanyaan), lalu tanya "isi kulkas 1?", "isi kulkas 2?", ... "isi kulkas 20?" (20 pertanyaan) = 21. Cara benar: tanya "daftar kulkas?" (1), lalu "isi semua kulkas sekaligus" (1) = 2, kemudian kamu kelompokkan sendiri di mejamu.

Perbaikan: ambil seluruh inventory sekali saja, lalu kelompokkan per warehouse memakai HashMap.

Bagian ini mengganti kode lama yang bertanya ke database sekali per gudang. Perhatikan pembagian tiga langkahnya: langkah 1–2 yang menyelesaikan N+1, sedangkan langkah 3 hanyalah merangkai jawaban seperti sebelumnya.

🔑Apa itu HashMap?

HashMap<i32, Vec<_>> adalah lemari dengan laci berlabel. Labelnya warehouse_id, isinya daftar inventory milik warehouse itu. entry(id).or_default().push(item) artinya: "buka laci berlabel id (buat kalau belum ada), lalu masukkan item ke dalamnya". Sesudah itu inventory_by_warehouse.remove(&warehouse.id) mengambil isi satu laci, tanpa bertanya ke database lagi.

Resep umum N+1 (kalau soal ujianmu berbeda)

Soal ujian bisa memakai tabel dan nama fungsi lain, tetapi polanya tetap sama. Yang perlu kamu kuasai adalah mengenali pola dan menerapkan tiga langkah ini.

🔑Cara mengenali N+1

Ada query database di dalam perulangan: for x in daftar { ... self.repository.xxx(x.id).await ... }. Jumlah query = 1 (daftar awal) + N (satu per elemen).

✅Yang benar-benar perlu dihafal

Cukup satu paket: peta.entry(kunci).or_default().push(item) (memasukkan ke laci) dan peta.remove(&id).unwrap_or_default() (mengambil laci). Sisanya menyesuaikan nama tabel dan kolom dari soal.

5.3 Courier Recommendation / Sort (3 poin)

Tujuan: Dispatcher melihat kurir yang tersedia, diurutkan dari yang paling cocok, berdasarkan jarak ke pabrik dan kecocokan region spesialisasi.

Rumusnya

🔑Skor kurir (0–100)

distance_score = 1 − (jarak ÷ 1280,625), dibatasi antara 0 dan 1.

specialty_score = 1 jika region spesialisasi kurir = region pabrik, selain itu 0.

score = (0,6 × distance_score + 0,4 × specialty_score) × 100

Angka 1280,625 adalah diagonal peta (1000 × 800), jarak terjauh yang mungkin, supaya skor jarak selalu di antara 0 dan 1.

Contoh hitungan (bisa kamu ulangi dengan kalkulator)

KurirJarakCocok region?distance_scoreSkor akhir
A200ya1 − 200/1280,625 = 0,8438(0,6×0,8438 + 0,4×1) × 100 = 90,63
B100tidak1 − 100/1280,625 = 0,9219(0,6×0,9219 + 0,4×0) × 100 = 55,31
C200tidak0,8438(0,6×0,8438) × 100 = 50,63

Kurir A lebih jauh dari B, tetapi menang karena cocok dengan region. Itulah makna "weighted": spesialisasi bobotnya 40% dan cukup besar untuk mengalahkan selisih jarak.

Bagian terpenting dipecah:

  1. Validasi

    Id tidak valid → 400; tidak ada → 404; status bukan 3 (READY_FOR_PICKUP) → 400, karena hanya order siap-ambil yang boleh di-dispatch.

  2. Filter kurir

    role_id == 2 (kurir) dan availability == 1 (tersedia). Operator lain dilewati dengan continue.

  3. Hitung jarak

    Rumus Pythagoras: sqrt(dx² + dy²) dari posisi kurir ke posisi pabrik.

  4. Hitung skor

    Rumus di atas, memakai konstanta DISTANCE_WEIGHT, SPECIALTY_WEIGHT, MAX_MAP_DISTANCE supaya mudah diubah.

  5. Urutkan

    sort_by(|a, b| b.score.total_cmp(&a.score)...): skor tertinggi di atas; kalau seri, yang lebih dekat dulu.

ℹ️Kenapa total_cmp dan bukan <?

f32 bisa bernilai NaN (bukan angka), sehingga Rust tidak memberi f32 urutan penuh dan tidak bisa langsung dipakai di sort(). total_cmp menyediakan urutan penuh yang aman.

7.3 Pertanyaan yang mungkin muncul

Kenapa memilih Set(0) dan bukan nilai lain untuk availability?

Di database availability bernilai 1 (tersedia) atau 0 (bertugas). Pemeriksaan di dispatch (!= 1) dan complete_task (Set(1)) memakai kamus nilai yang sama.

Apa bedanya unwrap() dan match?

unwrap() mengambil isi dan crash kalau ternyata Err/None. match memaksa kita menangani kedua kemungkinan. Project ini memeriksa is_err() dulu sebelum unwrap() supaya aman.

Apa itu hexagonal architecture di project ini?

Logika bisnis (service.rs) dipisah dari HTTP (server.rs) dan database (repository.rs), dihubungkan oleh trait (ServiceTrait, RepositoryTrait). Keuntungannya: database atau framework bisa diganti tanpa menyentuh aturan bisnis.

Kenapa fungsi trait memakai impl Future ... + Send?

Trait tidak bisa langsung berisi async fn yang dijamin aman lintas-thread, jadi ditulis sebagai fungsi yang mengembalikan Future yang Send. Server tokio menjalankan banyak tugas di banyak thread, jadi Future harus boleh dipindah antar-thread.

Apa yang kamu lakukan kalau tidak tahu jawabannya?

Katakan apa yang kamu ketahui, lalu "saya belum sepenuhnya yakin, tapi saya akan memeriksanya di kode" dan tunjukkan berkasnya. Penguji menilai kemampuan menelusuri dan menjelaskan, bukan hafalan.
